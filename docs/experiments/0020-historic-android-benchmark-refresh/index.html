Experiment description#

The project had useful Android benchmark numbers from earlier experiments, but some were aging and their original WAVs were no longer available to review. Experiment 0020 asked a simple question: if we rerun the exact same Supertonic CPU route on the authorized phone, do the old performance numbers still hold, and can we retain a trustworthy listening sample this time?

The experiment first audited the benchmark registry, then recreated the released-INT8 CPU route from experiment 0008 without modifying that frozen history. Old and new measurements stayed side by side so the refresh could reveal drift rather than silently replace the original result.

The rerun pinned the original model archive, sherpa-onnx 1.13.5 Android AAR, M1 voice (SID5), CPU provider, one thread, timing boundary, and actual-duration RTF calculation. It also reproduced the historical one-first-plus-three-warm protocol and the exact 230-byte legacy-v1 transcript with SHA-256 350c8d3d…471f.

That historical match is also the experiment's main limitation. Canonical v2 was adopted after this rerun and has different bytes, punctuation, and output duration. Experiment 0020 is therefore an old-versus-new check for the frozen legacy route, not a canonical-v2 benchmark. The refresh policy defines the 10% RTF comparison margin, evidence handling, and phone-safety rules.

The wider registry audit classified every visible full end-to-end route by transcript provenance and missing evidence. It found no canonical-v2 visible rows at that checkpoint: 17 used legacy v1 and nine used other noncanonical text. See the transcript provenance audit and normalization queue.

Progress#

  1. August 20, 2026: registry and route contract audited. The experiment recorded missing fields across the visible registry, preserved the original 0008 measurements, and froze the exact Supertonic refresh contract.
  2. Two native-Linux ADB readiness checks found no phone. Both stopped before staging. A later check through the pinned Windows adb.exe and audited shim reached the expected unlocked SM-S918B; the earlier zero-device observations remain valid for their timestamps.
  3. The first phone bootstrap exposed an Android 16 ownership problem. The package could not read shell-owned files under app-external scoped storage, so inference never started and the attempt produced no benchmark values or WAV.
  4. A second staging approach was also rejected. The final bounded adapter copied hash-verified inputs as the app UID into getFilesDir(). It left the frozen 0008 experiment untouched and changed no model, runtime, benchmark, timing, memory, or output behavior.
  5. The adapted route completed and cleaned up. The run waited for thermal eligibility without tuning the device, completed one first and three warm generations, pulled four hash-matched WAVs, then removed internal files, external output, and the package before releasing the phone lock.
  6. Moritz reviewed the retained median sample. On August 20, 2026, he marked the exact WAV 1cf003d5…ee6e “good.” The verdict applies only to the 0020 legacy-v1 refresh sample.

The blocked bootstrap remains visible in its result record. The adapted build provenance and staging and cleanup record document the route that finally ran.

It also did not record effective frontend IDs. Most importantly, the run used legacy v1 and only three warm generations. It must not be promoted as a canonical-v2, five-warm benchmark or compared as though its transcript matched experiments 0021 and 0022.
