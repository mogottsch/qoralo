Dynamic vs static quantization

Two ways to map floating-point neural-network values to INT8—and why the choice matters for Supertonic on Qualcomm HTP

The short version

Float activationValues produced by the previous layer
→
Measure rangeFind min/max while inference is running
→
QuantizeCalculate scale and convert to 8-bit integers
→
Integer matmulMultiply with pre-quantized weights
→
DequantizeConvert the result back to approximate floats
Dynamic means the activation scale is calculated from the current input every time the layer runs. It does not mean the same thing as a dynamically sized tensor.

Quantization formula

A floating-point value is represented by an integer code, a scale, and a zero point:

q = round(x / scale) + zero_point
x_approx = (q - zero_point) × scale

Quantization loses some precision because many float values map to the same integer code.

Runtime example

activation range: −1.20 … 0.95
scale = (0.95 − (−1.20)) / 255
scale ≈ 0.00843

x = 0.527 → q ≈ 191
q = 191 → x_approx ≈ 0.531

With dynamic quantization, a different input can produce a different range and scale.

Why it is attractive on CPU

  • No representative calibration dataset is required.
  • Ranges adapt to each input and flow step.
  • Weights are smaller than FP32 weights.
  • Integer matrix multiplication can be efficient on CPU.
  • It is a convenient general-purpose ONNX deployment transformation.

Why it is awkward for HTP

  • Quantization parameters are not known when QNN compiles the graph.
  • Range measurement and scale calculation become runtime graph operations.
  • QNN cannot fuse the complete sequence into one static accelerator graph.
  • Unsupported operations remain on CPU and split the graph into many partitions.
  • Every CPU↔HTP boundary adds orchestration, buffers, and possible data transfers.

Why dynamic quantization became popular for mobile CPU inference

1. It is almost drop-in

Developers can take a trained FP32 model, quantize its constant weights after training, and deploy it without recreating training data or building a calibration corpus. That makes it inexpensive to ship and easy for model repositories to distribute.

2. Model size and memory traffic improve

Large matrix weights shrink from 32 bits to 8 bits—roughly one quarter of the raw storage. Mobile CPUs are often limited by reading weights from memory, so smaller weights can matter even when activation quantization adds runtime work.

3. CPUs already handle irregular work

ARM and x86 CPUs have efficient integer dot-product instructions, but they also remain good at the small reductions, min/max scans, scalar scale calculations, and shape-dependent control needed around those kernels.

4. There is no accelerator boundary

On CPU, the range calculation and integer matrix multiplication run in the same process, address space, and memory hierarchy. A graph split is mostly another CPU kernel call—not an RPC and tensor transfer between CPU and a separate HTP device.

5. It adapts to variable inputs

Text lengths, acoustic values, and flow-estimator steps can have different activation ranges. Choosing a fresh scale for each tensor often preserves accuracy better than a poorly calibrated fixed range.

6. Runtime support is mature

Frameworks such as ONNX Runtime can recognize dynamic-quantized matrix multiplication and dispatch optimized CPU kernels. That gives publishers a broadly usable model without targeting one phone accelerator generation.

Important qualification: “popular” does not mean “always faster.” For small matrices, unsupported CPUs, or graphs with many quantize/dequantize operations, runtime range measurement can erase the gain. It is popular because it offers a practical size/accuracy/deployment compromise with very little model-preparation work.

The tradeoff: dynamic quantization moves range selection into inference; static quantization moves that work and risk into an offline calibration phase.
