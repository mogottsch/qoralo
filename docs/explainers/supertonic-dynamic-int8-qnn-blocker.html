Why runtime scale selection matters

For an INT8 tensor, the integer codes only have meaning together with a scale and zero point:

q = round(x / scale) + zero_point x ≈ (q - zero_point) × scale

In static quantization, those parameters are constants when QNN prepares the graph. In dynamic quantization, the model computes them from each current activation tensor:

minimum = ReduceMin(current_activation) maximum = ReduceMax(current_activation) scale, zero_point = choose_encoding(minimum, maximum) q = DynamicQuantizeLinear(current_activation, scale, zero_point) y_int = MatMulInteger(q, quantized_weights) y_float = rescale(y_int, activation_scale, weight_scale)
Compiler view: HTP graph preparation wants a stable tensor encoding, kernel contract, layouts, and boundaries. This ONNX representation makes range selection part of inference. In the pinned ORT 1.27.1 + QNN/QAIRT 2.49 stack, the relevant dynamic-quantization operators were not translated as one HTP subgraph.

ORT can execute this only when fallback is allowed. It schedules QNN subgraphs, CPU operations, and the boundaries between them. That is valid mixed execution, but it is not a single accelerator-resident model.

Fail-closed behavior was intentional: session.disable_cpu_ep_fallback=1 turned hidden partial execution into an explicit session-creation failure, preventing us from mislabeling a mixed graph as HTP execution.

Repeated-call consequence

Supertonic calls the vector estimator five times recursively for one utterance. In the later hybrid end-to-end run, four generations produced:

420QNN partition events
2,720CPU node events

That matches 20 vector calls × 21 QNN partitions and 20 × 136 CPU nodes. The profiler proved real HTP work, but also proved that the vector model was not fully delegated.

Dynamic shapes were a separate blocker

Dynamic shape

noisy_latent [B, 144, L] text_emb [B, 256, T]

The compiler initially rejected unspecified B, L, and T.

Dynamic quantization

scale = function(current_activation)

Even after fixing B=1, L=238, and T=239, the runtime quantization nodes remained unsupported.

Fixing tensor dimensions solved dynamic shape. It did not make activation encodings static.

The strongest comparison: official FP32 graph

The official public FP32 vector estimator contains the original inference graph before sherpa’s CPU-oriented dynamic quantization transformation. After only fixing graph I/O shapes, QNN accepted:

FP32 optimized graph868 nodes
QNN-supported867 nodes
Unsupported1 Softplus

Replacing that one Softplus with the stable equivalent Relu(x) + Log(1 + Exp(-Abs(x))) produced a completely delegated vector graph and physical HTP execution.

Concrete inference: the CPU-oriented dynamic-INT8 transformation introduced nearly all of the compatibility problem. ONNX itself was not the blocker, and HTP’s INT8 capability was not the blocker.

What would make INT8 compile more naturally?

Start from the official FP32 inference graph.
Do not try to reverse a graph already transformed for dynamic CPU quantization.
Collect representative activation data.
Cover real text, voices, lengths, seeds, and all five recursive vector steps.
Choose fixed scales offline.
Static QDQ embeds activation encodings as graph constants.
Run the fail-closed host QNN gate.
Require every node to map before touching the phone.
Validate physical accuracy and audio.
Static compilation is not proof that calibration preserved recursive behavior.

Precise claim

Too broad: “Dynamic quantization never works on HTP.” Supported by our evidence: “In the pinned Supertonic vector-estimator graph, ORT 1.27.1 and QNN/QAIRT 2.49 could not translate the DynamicQuantizeLinear, MatMulInteger, standalone per-channel DequantizeLinear, and Softplus nodes into a complete HTP graph. Fallback-disabled session creation therefore failed. The same model could run only as mixed QNN+CPU execution.”

Another QNN release, graph representation, operator set, or purpose-built backend could behave differently. The recorded conclusion is definitive for this artifact and stack.
