# Android benchmark dashboard operations

This document defines the durable maintenance procedure for `docs/android-benchmarks/`. Owning experiment records are the measurement source of truth; the generated registry is the normalized cross-experiment view.

## Source-of-truth order

1. Committed records under the owning `experiments/NNNN-*/` directory.
2. [`registry.json`](registry.json), deterministically generated by [`build_registry.py`](build_registry.py).
3. [`schema.json`](schema.json), [`validate.py`](validate.py), and [`missing-fields.md`](missing-fields.md).
4. [`index.html`](index.html) and identical [`dashboard.html`](dashboard.html) as generated presentation.

Messenger messages, ignored files, work directories, and uncommitted files are never sufficient ingestion evidence.

## Maintenance ownership

During coordinated multi-session work, one named session owns `docs/android-benchmarks/` exclusively. It reserves the directory, ingests committed experiment evidence, and uses scoped commits. Other experiment owners report commits and evidence but do not edit dashboard files.

## Required ingestion rules

1. Ingest only a scoped committed experiment result and independently inspect its machine record.
2. Verify every copied WAV SHA-256 and PCM16 header: size, channels, sample rate, sample count, and duration.
3. New comparable routes require canonical-v2 transcript SHA `424b38073a00cf48e4c3ebaa246aec0b6549b3ed56a1bf7cfa26d037fb29db67`, exact effective frontend output, setup, one first generation, at least five same-session warm generations with complete reset, actual-duration RTFs, memory semantics, runtime/provider/thread/device/thermal provenance, structural WAV evidence, and explicit listening status.
4. Preserve `warm_median_rtf`, `first_post_setup_rtf`, and `proof_run_rtf` as distinct fields. The compact RTF cell may choose one headline but must retain all values and labels in registry/details.
5. Only Moritz may set accepted or rejected, and only for the exact route and WAV hash recorded in committed evidence. Never inherit verdicts.
6. Host QNN/context evidence is feasibility only. Physical HTP requires fallback disabled, zero neural CPU events, every required call invoked, and matching RPC/accelerator/cycle/HVX proof.
7. Keep the registry exhaustive, but expose only complete `full_e2e` routes in the compact table. Blockers and probes remain `excluded_non_e2e` with null plus reason.
8. Preserve historical evidence. Add dated nested remeasurements or distinct derivative routes; never replace old values silently.
9. Use scoped staging and `git commit --only -- docs/android-benchmarks/...`; never reset or unstage peer work. Verify every dashboard commit with `git diff-tree`.

## Transcript classification

Canonical transcript v2 is the exact 226-byte, no-newline file at `protocols/android-tts-benchmark/transcript.txt`, SHA-256 `424b38073a00cf48e4c3ebaa246aec0b6549b3ed56a1bf7cfa26d037fb29db67`.

Visible routes are classified as:

- `canonical_v2` for that exact transcript;
- `legacy_v1` for the 230-byte historical transcript SHA `350c8d3d57525e65085b1d7c5ec733985c5467797cf50508b5e2a4eee313471f`;
- `noncanonical` for another known text;
- `unknown` only when retained evidence cannot establish the text, with an explicit reason.

Counts are generated state, not constants. Never infer a classification from model family or experiment number.

## Metric and listening boundaries

- `warm_median_rtf` exists only for a recorded warm distribution.
- `proof_run_rtf` is an instrumented or bounded proof run, not warm performance.
- `first_post_setup_rtf` is one first complete generation after setup.
- RTF is generation wall time divided by that run's actual emitted duration.
- Peak PSS and VmHWM/ru_maxrss retain their distinct source semantics.
- Technical execution, structural audio, numerical/acoustic evidence, and listening review remain separate.
- A playable sample stays `not_reviewed` until Moritz gives an exact-hash verdict.

## Regenerate and validate

Run from repository root:

```bash
python3 docs/android-benchmarks/build_registry.py
python3 docs/android-benchmarks/validate.py
git diff --check -- docs/android-benchmarks/
git status --short -- docs/android-benchmarks/
```

A deterministic rebuild must leave no unexplained diff. Then inspect JSON Schema, generated HTML, anchors, media links, sorting keys, transcript badges, missing reasons, and the owning experiment's tests.

## Adding a result

1. Reserve `docs/android-benchmarks/` during coordinated work.
2. Identify the newest committed experiment result not yet represented.
3. Verify its protocol, metrics, claim boundaries, and retained WAV independently.
4. Update the generator/schema/validator rather than patching generated HTML by hand.
5. Regenerate and validate.
6. Commit only dashboard paths and inspect `git diff-tree --no-commit-id --name-only -r HEAD`.
7. Report the dashboard commit and the exact evidence added or intentionally excluded.

The registry's current route/experiment/WAV counts are printed by the generator and validator; do not duplicate them here as a manually maintained status snapshot.
