Project history#

Goal and direction#

The project started by asking whether Microsoft's VibeVoice could generate a local two-speaker podcast on a modern Android phone. The goal later widened to finding any practical local TTS model that sounds pleasant and natural enough for a future NotebookLM-like listening experience.

Two-speaker generation remains desirable, but it is no longer mandatory. A strong narrator or persistent voices generated turn by turn can also meet the goal. Model quality, sustained listening, and practical Android deployment matter more than preserving the original VibeVoice architecture.

How result language is interpreted#

Completed experiments preserve distinct evidence classes:

  • technical execution means the declared path ran under its runtime/provider contract;
  • structurally valid audio means the WAV/container and numeric format/silence/clipping checks passed;
  • objective/descriptive comparison refers only to its named numerical or acoustic policy;
  • listening acceptance or rejection exists only when Moritz explicitly reviewed the exact route/sample.

These classes do not imply one another. In particular, “no audible difference” is a comparison between two samples, not acceptance of either sample's quality. An unreviewed route is not reviewed / unknown, and a route-specific rejection is not generalized to a model family. Frozen machine records keep their original status tokens and metrics; the narrative below explains their scope.

Experiment record#

Each summary links to the experiment that holds the detailed commands, measurements, artifacts, and limitations. Active experiments are intentionally not represented as completed outcomes.

Experiment Question at the time Result and consequence
0001: VibeVoice 1.5B host reference Can we create a fixed reference before attempting Android conversion? Produced the reproducible host CPU reference and evidence protocol. Human listening remained pending, so this was a technical reference rather than quality acceptance.
0002: VibeVoice 1.5B ExecuTorch Can the model run component by component and then end to end through ExecuTorch on Android? Individual components ran, but the complete fixed-shape path stopped after two near-silent chunks, covered only 2.04% of the reference, ran very slowly, and required about 9.1 GB. Later analysis showed that the quiet prefix closely matched the expected reference prefix, but it did not fix the capacity limit. The deployment was rejected by its technical/audio rubric; no positive listening acceptance was recorded.
0003: VibeVoice LiteRT Should the failed VibeVoice deployment be repeated with LiteRT? Deferred. A second full conversion was not justified while the model itself had not passed the practical deployment gate. No route or listening result exists.
0004: VibeVoice ONNX Runtime Should the same VibeVoice path be attempted with ONNX Runtime Mobile? Deferred for the same reason. No route or listening result exists.
0005: VibeVoice direct QNN Should direct Qualcomm acceleration be attempted for VibeVoice 1.5B? Deferred. Hardware-specific optimization was not justified before a correct portable route. No HTP audio or listening result exists.
0006: VibeVoice Realtime 0.5B Is the smaller VibeVoice model a more practical comparison? Recorded feasibility notes and storage estimates but produced no Android deployment. Moritz later ranked its exact host preview third behind Kokoro and Pocket in experiment 0007; that ranking did not explicitly accept or reject usability.
0007: Host listening bake-off Which smaller models sound promising enough to justify phone work? Moritz ranked the exact historical host previews Kokoro first, Pocket second, and VibeVoice Realtime third. This was a relative order among those three, not acceptance of any sample. Supertonic, Inflect, and Kitten were not reviewed; their listening quality is unknown.
0008: Android TTS benchmark How do Pocket, Kokoro, and Supertonic perform as pinned Android CPU deployments? All three completed their technical generation contracts and produced structurally valid WAVs. Supertonic 3 became the measured technical default with one-thread warm median RTF 0.370. No Android WAV was manually reviewed, so the experiment established no listening-quality winner.
0009: Android TTS optimization Can model size or CPU threading materially improve the selected candidates? The exact Kokoro mixed-INT8 candidate was 46.0% smaller. Its blind relative degradation gate yielded four ties, one low-confidence INT8 preference, and one low-confidence FP32 preference: no systematic degradation, but no absolute usability acceptance. All nine thread configurations completed; the sweep performed no listening review.
0010: Supertonic QNN/HTP feasibility Can the dominant Supertonic components run on the SM8550 HTP without hidden CPU fallback, and is acceleration worth its cost? Completed a fixed-transcript CPU/hybrid Android comparison. Hybrid used mixed QNN+CPU vector execution and a fully delegated vocoder, reducing warm generation from 6.067 to 3.809 s (37.2%) with physical accelerator proof. Session creation rose from 0.611 to 26.965 s and peak ru_maxrss from 459432 to 1154172 KiB. The prospective waveform gate failed. Moritz's no-audible-difference report remains comparison-only, but he later separately accepted both exact E2E samples as “Good.” CPU remains the technical reference; hybrid is a bounded research baseline.
0011: Supertonic official FP32 comparison Can official FP32 ONNX assets run on phone CPU and fully delegate to HTP? CPU and the stable-Softplus all-HTP route completed technically; all-HTP warm generation was 2.86× faster, but its prospective numerical policy failed. Moritz accepted the CPU sample as “Good—even a bit more crisp than samples 1 and 2” and accepted all-HTP as “Same as sample 3.” The latter is a perceptual comparison only, not numerical equivalence.
0012: Pocket FP ONNX versus ExecuTorch Can exact-source Pocket run through unquantized ONNX Runtime or ExecuTorch on Android CPU? FP ONNX completed the technical route at warm median RTF 0.630; ExecuTorch blocked before a complete model. Moritz blind-listened to retained CPU sample SHA 40634981606f37c59a91c14d99cecb3ef4cc21b1391882e870940b0716857d22 and rejected it as unusable repetitive “takakakakakakakaka.” This rejects that exact route/sample, not Pocket TTS as a family.
0013: Kokoro FP ONNX versus ExecuTorch Which exact-source unquantized CPU route is viable for official Kokoro v1.0? The fixed-contract ONNX route completed on Android at warm median RTF 0.9800; ExecuTorch blocked before a full-model PTE. A separate phase-tolerant acoustic policy passed, while the original strict waveform screen remained failed. Moritz accepted the exact retained CPU sample as “Good”; the verdict is sample-level.
0016: Pocket mixed QNN/CPU Does allowing CPU fallback make the existing Pocket graphs a useful HTP acceleration route? The route physically used HTP but regressed warm RTF from 0.630 to 1.003 and changed EOS from 78 to 48 latent frames. It failed acceleration/equivalence objectives. Moritz rejected the exact hybrid sample as “takataktaka.” This is route/sample-only and is not a Pocket-family rejection.
0017: Kokoro QNN/HTP feasibility Can the exact-source-derived Kokoro ONNX graph execute fail-closed through QNN HTP? A narrow derivative became CPU-bit-identical and fully QNN-assignable, but host graph sequencing was kernel-OOM-killed at 64% before session finalization or inference. No QNN audio exists, so no listening verdict is applicable.
0018: MOSS-TTS-Nano ONNX CPU Can the official MOSS-TTS-Nano ONNX path run end to end on Android CPU? The route completed technically and produced a structurally valid 16.72-second WAV, but warm median RTF was 1.125 and process memory was large. Moritz accepted the exact sample as “Okay to good, but with a bit of a Chinese accent.”

Decisions carried forward#

  • The repository covers the TTS layer only. Source ingestion, retrieval, script generation, application UI, and episode management belong to the later product.
  • Pleasant, natural long-form speech is the primary goal. Joint multi-speaker generation is useful but optional.
  • Full-context generation is preferred. Naive sentence or clause splitting was rejected because it can damage prosody and naturalness.
  • Supertonic 3 CPU remains the supported Android technical reference. That designation is technical; separately, Moritz accepted the exact experiment-0010 CPU sample as “Good,” without establishing broad-corpus quality.
  • Full-HTP claims must fail closed. Explicit mixed execution must be labeled as mixed and supported by provider-level plus physical-device profiling evidence; partial delegation is never full HTP.
  • Experiment 0010's “no audible difference” result remains comparison-only evidence; separate later verdicts accept both exact E2E samples as “Good.” The hybrid remains numerically rejected and is not an adopted deployment.
  • Experiments 0012 and 0016 reject their exact retained Pocket route/samples for listening use. Neither verdict rejects Pocket TTS as a family.
  • Kokoro 0013 has an exact-sample “Good” verdict. MOSS 0018 has an “Okay to good” verdict with a Chinese-accent caveat. Neither sample-level verdict establishes broad-corpus quality.
  • A numerical/acoustic gate pass, structurally valid WAV, relative degradation ballot, or provider success must never be rewritten as absolute listening acceptance.
  • Qualcomm software and generated restricted artifacts stay local. New terms, logins, consent, or export gates require explicit human approval.
