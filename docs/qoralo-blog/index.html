Building a NotebookLM-like podcast on my phone

You've probably heard of NotebookLM. Feed it a few sources and it makes a podcast-style conversation. The output isn't as good as a real podcast, and it gives me some AI slop vibes. But it's still pretty impressive.

So I wondered: how good could this be with all inference running on my phone?

The phone version

The prototype writes a script, then reads it in one voice. Model preparation and compilation happen on a computer; inference runs on my Galaxy S23 Ultra.

The first Android port

Before Supertonic, we tried Pocket TTS. It spoke this sentence normally on the desktop. On the phone's CPU the audio ran 10.72 seconds instead of 4.48 and sounded unhinged.

Pocket TTS runs entirely on this Android phone using the original floating point model.

Why it went wrong

The first generation step takes a special input. The graph checks it with Where(IsNaN(x), bos_emb, x): if the values are NaN, it swaps in the learned start-of-sequence vector. The C++ runner passed 32 NaNs to mean “start here.”

The phone's stop scores stay below the stop threshold for all 134 frames. I replayed the model on a desktop with the same text, voice cache and noise, changing only the first input. All zeros reproduces the phone's scores closely. NaN doesn't. I also tried 62 inputs with only a prefix or suffix zeroed, and none matched.

Zeros are inferred, not observed: I didn't read the phone's memory. They are consistent with the old runner, which builds the NaN buffer inside an if block, wraps it in a tensor that doesn't own it, and frees it before calling Run().

if (step == 0) {
  std::vector<float> bos(32, NaN);
  inputs.push_back(TV(mi, bos, {1, 1, 32}));
} // bos is freed here
Run(main, inputs); // the tensor still points at it

The learned start vector is small, with an L2 norm of 0.17, so zeros move the first stop score by only 0.39. But every later frame is conditioned on that step's cache and on the previous frame. The difference compounds, the stop score never crosses −4, and the model keeps talking until the 134-frame cap.

The fix we applied

We didn't find this bug at the time. The fixed-cache graphs were built for the NPU: static 256-slot caches, explicit positions and a separate first-step graph with the start vector built in. That version has no NaN marker to lose. Its stop scores on the same phone CPU match the desktop replay's within 0.0021.

One different input at the first step produced a valid-looking file that sounded wrong. Compare first-step inputs and scores across devices, not only the finished audio.

Sources & technical notes

The replay ports the old runner's loop to ONNX Runtime 1.22.1 on a desktop CPU and changes only the first autoregressive input. It reuses the retained fixed-Alba cache, token IDs and noise fixture, whose hashes are checked. The exact original flow_lm_main graph is not retained. The replay uses a same-size reconstruction with a different hash. It reproduces the original desktop run: first stop score −9.8847 and stop at step 53. It also matches the Android fixed-cache stop scores within 0.0021.

With all-zero input the replay's 134 stop scores differ from the retained Android run by at most 0.074, mean 0.006, and never reach the threshold. With the correct NaN input they differ by up to 16.4 over the 57 frames before it stops. The replay produced no audio and makes no listening claim.

Not shown: the phone's freed-buffer contents, which were not read, and that the retained source is exactly what was built into the old phone executable. The dangling read itself is confirmed in source and by a host AddressSanitizer test that uses ONNX Runtime's real non-owning tensor API and no model. The earlier invalid-voice-clone failure is a different cause.
