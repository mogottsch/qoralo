Building a NotebookLM-like podcast on my phone

You've probably heard of NotebookLM. Feed it a few sources and it makes a podcast-style conversation. The output isn't as good as a real podcast, and it gives me some AI slop vibes. But it's still pretty impressive.

So I wondered: how good could this be with all inference running on my phone?

The phone version

The prototype writes a script, then reads it in one voice. Model preparation and compilation happen on a computer; inference runs on my Galaxy S23 Ultra.

The first Android port

The errors you run into while working on TTS can be interesting. Before Supertonic, we tried Pocket TTS. On my laptop it said this sentence fine. Here it is twice on my phone's CPU, with the same weights, text, voice and noise. The first sounds right. The second is our first port, and it runs 10.72 seconds instead of 4.48 and sounds unhinged.

Pocket TTS runs entirely on this Android phone using the original floating point model.

Why it went wrong

The model expects a special NaN marker as its first input and swaps in its learned start vector. Our phone code freed that buffer too early, so the model got zeros instead. It started from the wrong place and never found the end, so it kept talking until we cut it off. The voice went wrong too, because every sound it makes is built on that wrong start.

The old runner builds the NaN buffer inside an if block, hands the model a pointer to it, and frees it before Run(). Reading freed memory is undefined behavior. On the phone it read as zeros.

if (step == 0) {
  std::vector<float> bos(32, NaN);
  inputs.push_back(TV(mi, bos, {1, 1, 32}));
} // bos is freed here
Run(main, inputs); // the tensor still points at it

The fix we applied

We didn't find this bug at the time. The fix came with porting the graphs to the NPU: that version has the start vector built in, so there is no NaN marker to lose.

One different input at the first step produced a valid-looking file that sounded wrong. Compare first-step inputs and scores across devices, not only the finished audio.

Sources & technical notes

Phone check: on the Galaxy S23 Ultra, CPU only, ONNX Runtime 1.27.1, I rebuilt the retained runner and ran four versions twice in one window. They were the unmodified source, a build that prints the 32 start values to stderr right before inference, a build that only keeps the buffer alive, and both changes. With the original lifetime the printed values were all zero, 2 of 2 runs. With the buffer kept alive they were all NaN, 2 of 2. The four kept-alive runs gave identical stop scores and audio, with a stop at frame 53. Their audio correlates 0.999996 with the earlier accepted fixed-cache recording. I made no new listening judgment.

Desktop replay: the old runner's loop on ONNX Runtime 1.22.1 on a desktop CPU, changing only the first autoregressive input, with the retained fixed-Alba cache, token IDs and noise. All zeros gives 134 stop scores within 0.074 of the retained Android run (mean 0.006) with no stop. NaN gives scores that differ by up to 16.4 over the 57 frames before it stops. I also tried 62 inputs with only a prefix or suffix zeroed, and none matched. Measured as the difference divided by the correct run's size, the zero-input internal state is off by 1.05 at the first frame (median 1.21 over the 56 frames) and the frame itself by 0.76 (median 1.36). The stop score and the next frame are both read from that internal state in the model's source, and each frame is fed back as the next input in the runner's loop.

Limits: the old phone executable is not retained, so the unmodified source was rebuilt with NDK 27. The exact original flow_lm_main graph is also missing. I used a same-size reconstruction with a different hash. It reproduced the old desktop run, and on the phone it reproduced the old failure recording byte for byte. The dump build may change allocation, and the unmodified build's start values were never printed. The second unmodified run gave a different result (first stop score −4.37, still no stop), so this failure is not deterministic. I have no explanation for why this allocator returned zeros. The earlier invalid-voice-clone failure is a different cause.
