**1. Engine profile**  
- **Cedar** – a compact model that starts up quickly but decodes slowly. Its generation is steady, so once the model is loaded the latency per token is low. It uses the least amount of memory, which is advantageous on devices with tight RAM limits.  
- **Juniper** – spends a longer time preparing its model, but it processes prompts more steadily. The trade‑off is a higher initial “time‑to‑first‑token” (prefill) but a more predictable token‑generation rate.  
- **Rowan** – consumes more memory than Cedar but can accelerate prompt processing. It is best suited for workloads where many short prompts are issued in rapid succession and memory is not the primary bottleneck.

**2. Application context**  
The application stays open for twenty to forty minutes. Some users close the app after a single request, while others keep it open for the whole session. Because the device has limited memory and the operating system may reclaim background processes under pressure, the recommendation must treat *cold* (first‑time) and *warm* (re‑used) sessions differently.

Use Juniper when many short prompts are issued in quick succession. |

**4. Measurements that must stay separate**  

- **Time‑to‑first‑token (prefill latency)** – the interval from when the user sends a prompt until the first token is emitted. This isolates the model‑loading cost.  
- **Decode throughput** – tokens generated per second after the first token. This reflects the engine’s steady‑state performance.  
- **Peak memory usage** – the maximum size of the key‑value cache and any mapped model files during a session.  
- **High‑water‑mark (HWM) size** – the total memory allocated for the session, which includes both model and runtime structures.  
- **Thermal delta** – temperature change (°C) before and after a campaign, and average power draw (mA) during generation.  
- **Token count** – total number of tokens (including special tokens) produced for each request, recorded per engine.

These metrics should be logged in separate time‑series streams, not aggregated into a single “overall latency” metric, because they each answer a distinct question about the system’s behavior.
