The team must prioritize a unified evaluation framework that treats setup time, prompt processing, and token generation as distinct, non-overlapping phases. Engine Cedar's speed in opening the model comes at the cost of slow decoding, while Juniper's steady generation is offset by longer preparation times, and Rowan's speed comes with a memory penalty. To make a fair comparison, the metrics must be isolated strictly by these three phases; any metric that conflates setup with generation or mixes prompt processing with decoding will invalidate the results.

Regarding session management, the application's typical twenty-to-forty-minute runtime is a critical constraint. A route with expensive setup is only viable if the loaded session is reused, meaning the evaluation must account for the cumulative cost of a one-request visit and a longer session without artificially combining their timing boundaries. The device's limited memory and the OS's aggressive background process reclamation introduce significant variability. Mapped model files, private anonymous allocations, shared pages, runtime workspaces, and the growing key-value cache do not share identical memory semantics; therefore, peak sampled proportional set size and process high-water marks must be labeled distinctly rather than treated as interchangeable resources.

Prompt length variability further complicates the data. Token counts differ across model tokenizers even when the exact UTF-8 prompt bytes are identical, and time to first token includes work a user experiences before text appears, whereas prefill throughput isolates processing of the input tokens. A runtime that exposes only a combined timing cannot be credited with an invented split between prefill and sampling.
