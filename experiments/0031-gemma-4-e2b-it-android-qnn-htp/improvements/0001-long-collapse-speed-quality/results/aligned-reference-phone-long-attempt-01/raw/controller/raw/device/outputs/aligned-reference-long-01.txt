This brief outlines a rigorous framework for comparing local inference engines on a battery-powered device, emphasizing the need for granular, context-aware measurements over simple aggregate performance metrics. The core challenge is to accurately isolate the impact of model loading, prompt handling, and token generation across different inference engines—Cedar, Juniper, and Rowan—while acknowledging the inherent instability of the mobile environment.

A critical aspect of the analysis must be the clear separation of timing components. We must distinguish between the time spent on setup, the time dedicated to prompt processing (prefill), and the time spent on generating the output (decode throughput). A single combined timing metric is insufficient because it obscures the specific trade-offs between these phases. For instance, Engine Cedar might excel at quick setup but suffer from slow decoding, whereas Engine Rowan prioritizes fast prompt processing at the expense of memory. These distinct behaviors must be quantified separately.

Memory management requires careful attention. Given the device constraints and the varied memory semantics of different allocations (mapped files, caches, key-value stores), simply measuring peak memory usage is inadequate. We must track specific high-water marks for distinct memory components, such as the sampled proportional set size and process high-water marks, rather than treating all memory as a monolithic entity.

Prompt variation is also a significant factor. The performance metrics must be segmented by prompt tier—short, medium, and long requests—as token counts and prefill costs vary substantially across these lengths. Furthermore, the tokenizer and template behavior must be explicitly recorded, as they can independently influence token counts, independent of the model weights themselves.

The process of execution must be transparent. We need to account for initialization events that can occur on the first request—such as page faults or accelerator compilation—and ensure that repeated requests clear state while preserving the loaded model session. The report must explicitly separate the initial observation from the distribution of subsequent requests to capture this transient effects.

Finally, the output quality assessment must be decoupled from raw speed. While performance measures like decode throughput are vital, the system sanity check should focus on the raw output bytes to ensure the result is not merely syntactically broken but also semantically plausible. Provenance tracking is equally important; every artifact used model or conversion must be linked to its source revision, file hash, and quantization method to ensure reproducibility.

The primary trade-off to manage is the balance between raw speed and resource consumption. A route optimization should not be judged solely on the fastest token generation rate; it must be evaluated against the overall practicality, considering setup time, memory footprint, and the specific prompt lengths the application is expected to handle. A route recommendations should articulate these trade-offs clearly, explaining *why* a slower but more memory-efficient route might be preferable for a specific use case, rather than simply declaring one engine superior overall.

The practical next step is to define the specific, measurable checkpoints for the three engines across the defined prompt tiers, ensuring that each measurement explicitly labels its origin—setup, prefill, or decode—and its associated resource consumption—memory, thermal, and power state—to build a comprehensive, evidence-based comparison that informs the decision for deeper deployment.
